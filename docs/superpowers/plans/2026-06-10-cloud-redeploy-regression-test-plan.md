## 1. 测试目标

本计划用于验证 Nomi 在私有云服务器重装、Docker 环境重建、Android 真机接入后的关键产品链路是否恢复可用。它不是替代 2026-06-08 的全量产品回归文档，而是作为本轮部署后的专项回归计划，优先覆盖最近实际暴露的问题：

- 私有云服务能否稳定启动，Docker、数据库、Redis、Runtime API、Model Router、Worker、Web/nginx、noVNC 是否连通。
- 模型路由是否正确调用 `qwen3.6`，不能出现 `/v1/v1/chat/completions` 这类路径错误。
- Runtime API 启动不能被 embedding warmup 阻塞。
- Android 悬浮对话框不能闪烁，键盘不能遮挡输入框，发送不能 silent timeout。
- 求职看板接口不能 404，并且输出应是具体、可解释、可操作的求职状态。
- 私有事件进入记忆、日程、主动建议的链路必须输出合理内容，不只是返回成功。
- Composio/第三方授权、受控浏览器、Nomi 自有身份、语音输入等 provider-gated 功能必须清楚区分已通过、配置阻塞、设备权限阻塞、真实功能失败。

## 2. 验收原则

每一条测试都必须判断“输出是否正确且合理”，不能只看进程、HTTP 状态码或测试命令是否成功。

通过标准：

- 传输层成功：请求能到达正确服务，响应状态符合预期。
- 结构层正确：响应 JSON 字段完整，状态枚举、ID、trace、evidence、error code 可审计。
- 语义层合理：模型回复、日程、建议、Pipeline 结果与输入事实一致，没有编造、混淆联系人、相对日期不落地、误称已执行真实动作。
- 产品层可用：Android/Web 用户能看懂结果，失败时有明确提示，关键操作有下一步按钮或可恢复路径。
- 安全层合格：日志、响应、截图、测试报告不暴露 token、cookie、密码、验证码、authorization header。

状态分类：

| 状态 | 含义 |
| --- | --- |
| `passed` | 功能真实通过，且输出语义合理 |
| `failed` | 功能可执行但输出错误、不合理或用户不可用 |
| `blocked_by_provider_config` | 依赖 Composio、Gmail、WhatsApp、SMS、电话、地图等 provider 配置，当前缺授权或缺账号 |
| `blocked_by_device_permission` | 依赖 Android 权限、悬浮窗权限、麦克风权限或真机状态 |
| `blocked_by_model_service` | 依赖模型服务，但模型服务不可达或返回异常 |
| `blocked_by_infra` | Docker、网络、安全组、数据库、SSH、磁盘等基础设施阻塞 |
| `skipped_by_scope` | 本轮明确不测，必须写明原因和补测条件 |

## 4. 执行顺序与并行策略

### 4.1 第一批可并行预检

这些测试互不依赖，可并行执行：

- A1：本地代码静态检查和单元测试。
- A2：服务器 SSH、Docker、容器健康、日志扫描。
- A3：线上 `/health`、Web 首页、noVNC 页面、基础 API 连通性。
- A4：Model Router 直连和 Runtime API 模型调用。
- A5：Android 构建和 APK 安装前检查。

### 4.2 第二批可并行功能冒烟

第一批通过后可并行执行：

- B1：Web 工作台对话、流式输出、错误提示。
- B2：Android 悬浮球、对话框、键盘、发送状态、历史恢复。
- B3：受控浏览器 Gmail/WhatsApp/Telegram 页面打开与关闭。
- B4：求职看板、日程、主动建议页面接口。
- B5：记忆检索、Pipeline 路由、Long-tail Agent dry-run。

### 4.3 必须串行执行的测试

以下测试有状态依赖，不能随意并行：

1. 私有事件采集 -> 事件账本 -> 语义事件 -> 记忆 -> 日程 -> 主动建议。
2. 主动建议 -> Android 气泡展示 -> 用户点击 -> 对话页面承接上下文。
3. 用户目标 -> Pipeline/Agent 路由 -> 执行计划 -> 工具确认 -> 最终回复。
4. Composio 连接 -> callback 返回 -> 授权列表刷新 -> provider-gated 动作。

## 5. 预检用例

### CR-PRE-001 服务器 SSH 与端口连通

目的：确认本地到私有云的 SSH、HTTP、HTTPS、noVNC 网络路径没有被 VPN、安全组或 known_hosts 问题阻断。

步骤：

1. 关闭或确认 VPN TUN 模式不会影响目标 IP。
2. 使用本地脚本或手动命令测试 SSH 端口。
3. 请求 `http://206.119.171.141/health`。
4. 请求 `http://206.119.171.141:6080/vnc.html`。

期望：

- SSH 端口能建立连接或明确进入认证阶段。
- `/health` 返回 `{"status":"ok"}` 或等价健康 JSON。
- noVNC 页面返回 HTML，而不是连接超时或 403。
- 如果失败，必须能区分本地网络、服务器防火墙、安全组、sshd 配置、known_hosts 哪一类。

### CR-PRE-002 Docker 服务拓扑

目的：确认重装后的 Docker compose 服务完整运行。

步骤：

1. 在服务器项目目录执行 `docker compose ps`。
2. 检查 `postgres`、`redis`、`runtime-api`、`worker`、`model-router`、`nginx`、`chromium-runtime`。
3. 扫描最近日志中的 `error|exception|traceback|502|connection refused|address already in use`。

期望：

- 关键服务均为 running/healthy。
- 不存在持续重启。
- 日志中允许一次性启动 warning，但不能有持续请求失败、数据库连接失败、模型 URL 错误。

### CR-PRE-003 Runtime API 启动不被 embedding 阻塞

目的：验证 embedding warmup 失败或变慢时不会阻塞 API 生命周期。

步骤：

1. 重启 `runtime-api`。
2. 立即请求 `/health`。
3. 查看 embedding warmup 相关日志。
4. 执行对应单元测试。

期望：

- `/health` 在合理时间内返回。
- embedding warmup 即使失败，也应记录为后台 warmup 错误，不导致 Runtime API 启动失败。
- 单元测试应覆盖该行为。

### CR-PRE-004 Model Router qwen3.6 调用

目的：确认模型路由可用，且不会重复拼接 `/v1`。

步骤：

1. 请求 Model Router 的 chat/completions 测试接口或 Runtime API `/api/chat`。
2. 输入简单中文：“请只回复：模型可用”。
3. 检查 Model Router 日志中的实际上游 URL。

期望：

- 返回内容应包含“模型可用”或语义等价内容。
- 日志中不能出现 `/v1/v1/chat/completions`。
- 如果模型不可用，前端和 API 都必须返回明确错误，而不是空白、无限 loading 或 timeout silent failure。

## 6. Web 与 API 对话用例

### CR-CHAT-001 Web 对话基础回复

目的：确认用户从 Web 工作台发送消息能得到合理回复。

步骤：

1. 打开 Web 工作台。
2. 输入：“Nomi，线上服务恢复了吗？请用一句话回答。”
3. 观察流式输出或最终回复。
4. 检查响应 trace/context 是否存在。

期望：

- 回复应明确回答服务状态，不能转移话题。
- 如果模型异常，应显示失败原因和重试入口。
- 请求不应超过配置超时时间后无提示失败。

### CR-CHAT-002 上下文连续性

目的：验证对话上下文不是只取极短条数导致“需要”这类短回复无法理解。

步骤：

1. 发送：“我有一个 PHONE_1 客户报价，周五 18:00 截止，可能需要核对成本和利润率。”
2. 等待 Nomi 追问或建议。
3. 回复：“需要。”
4. 观察 Nomi 是否能理解“需要”指核对成本与利润率。

期望：

- Nomi 应承接上一轮语义，不能说“不知道需要指什么”。
- 如果仍缺信息，应追问具体缺的成本项，而不是否认上下文。
- trace 中 context pack 应包含相关上一轮消息或摘要。

### CR-CHAT-003 WebSocket/流式输出

目的：验证完整工作台对话流式输出可用。

步骤：

1. 发起需要多句回答的问题。
2. 观察前端是否逐步渲染。
3. 中途网络慢时查看是否有 loading/typing 状态。

期望：

- 用户能看到渐进输出或明确的等待状态。
- 结束后消息落库，可刷新恢复。
- 不能出现重复 token、乱码、半截 JSON 暴露给用户。

## 7. Android 真机与模拟器用例

### CR-AND-001 悬浮球默认状态

目的：确认启动后默认只有 Nomi 悬浮球，点击后才打开对话框。

步骤：

1. 安装最新 APK。
2. 授予悬浮窗权限。
3. 回到桌面观察。
4. 点击悬浮球。

期望：

- 默认只显示一个 Nomi 小人悬浮球。
- 点击后打开对话框。
- 关闭对话框后悬浮球仍存在。

### CR-AND-002 对话框关闭不杀悬浮球

目的：回归右上角关闭按钮行为。

步骤：

1. 打开悬浮对话框。
2. 点击右上角关闭按钮。
3. 观察桌面。
4. 再次点击悬浮球。

期望：

- 对话框关闭。
- 悬浮球仍在。
- 再次点击能重新打开。

### CR-AND-003 输入框与键盘布局

目的：验证键盘弹出后输入框被顶到键盘上方，内容可见。

步骤：

1. 打开对话框。
2. 点击输入框。
3. 在模拟器和 Redmi 真机分别输入一段中文。
4. 点击发送。
5. 点击聊天内容区域收起键盘。

期望：

- 点击输入框自动弹出键盘。
- 输入框位于键盘上方，用户能看见正在输入内容。
- 点击发送后键盘不自动收起。
- 只有点击聊天内容区域或键盘收起按钮时才收起。
- 对话框不应狂闪、重复叠加或生成多个半透明窗口。

### CR-AND-004 发送状态与失败提示

目的：避免“发送失败 timeout”或 silent failure。

步骤：

1. 在 Android 对话框输入：“ping，请回复 pong。”
2. 点击发送。
3. 观察用户消息、loading、AI 回复或错误提示。

期望：

- 用户消息立即显示。
- 请求中显示可见 loading 或 pending 状态。
- 成功时 Nomi 回复语义应包含 pong 或等价确认。
- 失败时展示具体错误和重试按钮，不能只出现空白气泡。

### CR-AND-005 历史对话重启恢复

目的：确认重启 App/模拟器/真机后历史对话仍在。

步骤：

1. 发送一条带唯一 ID 的消息，例如 `RG_CHAT_<run_id>`。
2. 确认 Nomi 回复。
3. 杀掉 App 或重启设备。
4. 重新打开悬浮球。

期望：

- 历史对话恢复。
- 如果远端不可用，应显示本地缓存或明确“远端同步失败”，不能空白且无解释。

### CR-AND-006 主动消息气泡

目的：验证主动建议能在悬浮球旁展示气泡，并点击进入对话。

步骤：

1. 注入一条会触发主动建议的私有事件。
2. 等待 WebSocket 推送。
3. 观察悬浮球气泡。
4. 点击气泡。

期望：

- 气泡展示摘要，不遮挡主屏核心区域。
- 点击后进入对话页面。
- 对话中包含该建议的上下文和可点击选项，例如“查路线”“稍后提醒”“忽略”。

## 8. 受控浏览器与账号授权用例

### CR-BRW-001 noVNC 页面可用

目的：确认受控浏览器入口可打开并可关闭。

步骤：

1. 打开 noVNC 页面。
2. 登录 VNC。
3. 打开受控浏览器。
4. 点击关闭按钮。

期望：

- 画面尺寸合理，不黑屏。
- 浏览器可打开页面。
- 关闭按钮有效。

### CR-BRW-002 登录渠道打开正确页面

目的：回归“点 Telegram 却打开 WhatsApp”的问题。

步骤：

1. 在 Nomi 设置页进入账号连接。
2. 分别点击 Gmail、WhatsApp、Telegram。
3. 记录打开的 URL、页面标题和渠道名称。

期望：

- Gmail 打开 Google/Composio Gmail 授权相关页面。
- WhatsApp 打开 WhatsApp Web 或对应连接页面。
- Telegram 打开 Telegram 对应连接页面。
- 任何渠道不能复用上一渠道残留页面。

### CR-BRW-003 授权成功后返回列表

目的：避免 Composio 成功页卡死。

步骤：

1. 发起一个 provider 授权。
2. 完成授权或使用测试回调。
3. 观察页面返回。

期望：

- 成功后自动或通过明确按钮返回 Nomi 授权列表。
- 授权列表刷新 connected 状态。
- 不能停在“Successfully connected, you can close this window now”且无关闭入口。

### CR-BRW-004 不自动弹授权

目的：回归启动后莫名弹 Composio 授权的问题。

步骤：

1. 冷启动 Android App。
2. 不点击账号连接。
3. 等待 60 秒。

期望：

- 不应自动打开外部授权页面。
- 只有用户显式点击某个渠道连接时才触发授权。

## 9. 私有事件、记忆、日程与主动建议

### CR-MEM-001 WhatsApp/Gmail/Telegram 事件入库

目的：验证渠道事件能写入原始事件账本和长期记忆。

步骤：

1. 构造或接收 WhatsApp 测试消息：`RG_<run_id> 明天下午4点在人民广场见，带合同。`

4. 查询事件账本、语义事件、记忆检索。

期望：

- 每条事件有 channel、source_id、timestamp、conversation/contact scope。
- 记忆可检索到对应事实。
- 不同联系人/渠道作用域隔离，不能把 B 对 A 的评价召回给 A。

### CR-AGD-001 相对时间必须归一为具体日期

目的：回归日程页面显示“明天下午4点”但不知道是哪天的问题。

步骤：

期望：

- 日程卡片主标题和详情必须显示具体日期，例如 `2026-06-11 16:00`。
- 可保留原文“明天下午4点”作为 evidence，但不能只显示相对时间。
- 如果创建时间缺失，应标记 `time_ambiguous` 并要求补充，不应生成确定日程。

### CR-AGD-002 周视图 Tab

目的：验证日程管理顶部按周一、周二、周三等切换。

步骤：

2. 查看顶部日期 Tab。

期望：

- Tab 显示星期和具体日期。
- 当天 Tab 明确高亮。

### CR-PRO-001 主动建议语义合理

目的：确认主动建议不是简单复读，而是基于事件类型给出正确动作。

步骤：

1. 输入约见事件。
2. 输入报价截止事件。
3. 输入购物/付款/出行事件。
4. 观察主动建议。

期望：

- 出行事件可以建议“查路线”“帮我打车”，但打车必须等用户确认。
- 不应在没有用户确认时声称已经打车、付款或发送消息。

## 10. 求职 Agent 与核心 Pipeline

### CR-JOB-001 求职看板不 404

目的：回归“求职 tab 加载失败 http404”问题。

步骤：

1. 打开求职入口。
2. 请求求职看板 API。
3. 观察页面状态。

期望：

- 不返回 404。
- 没有数据时显示空状态和创建求职目标入口。
- 有数据时显示岗位、阶段、下一步、风险、最近沟通、截止时间。

### CR-JOB-002 JD + 简历匹配

目的：验证 Job Agent 的核心价值，不只是存岗位。

步骤：

1. 输入一份 JD fixture。
2. 输入用户简历 fixture。
3. 请求匹配分析。

期望：

- 输出匹配分、强匹配点、缺口、简历修改建议。
- 建议必须引用 JD 和简历证据。
- 不能编造简历中不存在的经历。

### CR-JOB-003 自我介绍和私信草稿

目的：验证联系 HR/面试官草稿结合 JD 和简历。

步骤：

1. 选择岗位。
2. 选择目标联系人 HR。
3. 生成 LinkedIn/邮件/WhatsApp 私信草稿。

### 17.1 基础设施预检

#### CR-PRE-001 服务器 SSH 与端口连通

| 步骤 | 操作 | 每一步预期结果 | 合理性判断 | 失败判定 |
| --- | --- | --- | --- | --- |
| 1 | 确认本地 VPN/TUN 状态并记录出口 IP | 能明确记录本地当前网络状态；如果 VPN 开启，应记录是否可能影响到目标服务器连接 | 记录必须能解释后续 SSH 失败是否可能来自本地出口变化 | 未记录网络状态直接测试，失败原因不可归因 |
| 2 | 测试 `206.119.171.141:22` TCP 连通 | TCP 至少进入 connected 或 SSH banner 阶段 | 如果连接被拒绝，应能区分端口未开、sshd 未监听、安全组阻断 | 只写“连不上”，没有错误类型 |

| 2 | 扫描服务端日志 | 错误日志不打印 authorization header | trace id 可以保留 | 日志含完整密钥 |
| 3 | 触发前端错误 | UI 只显示错误类型和 trace id | 用户可报告问题但不泄密 | 弹窗展示 token |
| 4 | 导出回归报告 | 报告可公开给开发者排查 | 敏感值已脱敏 | 报告不可分享 |

## 18. 单条用例通过判定规则

一条用例只有同时满足以下条件，才能标记为 `passed`：

1. 所有步骤都有实际输出记录。
2. 每一步的实际输出与“每一步预期结果”一致，或存在合理等价输出。
3. 语义判断没有发现事实错误、联系人混淆、渠道混淆、相对日期未落地、未授权动作伪成功。
4. UI 用例必须有截图或人工观察记录；真机闪烁、遮挡、空白气泡这类问题以人工观察为准。
5. provider-gated 用例在未授权时只能标记为阻塞或正确阻断，不能标记为真实通过。
6. 测试日志和报告没有泄露敏感信息。

如果某一步失败，整条用例必须标记为 `failed` 或对应 `blocked_*`，并写明：

- 失败步骤编号。
- 实际输出。
- 与预期差异。
- 用户可见影响。
- 需要修复的模块或解除阻塞的条件。
