# 2026-07-02 WhatsApp 真实消息稳定性回归测试计划

## 目标

用真实 WhatsApp 对话消息验证 Nomi 的 WhatsApp 采集、记忆写入、语义解析、日程创建、主动建议、问答召回和去重能力。

这轮测试不使用 `NOMI_` 前缀，消息尽量模拟真人自然表达。每批消息发送后都必须检查实际输出是否合理，不能只看接口是否成功。

## 测试基线

- 当前日期：2026-07-02，Asia/Shanghai。
- 测试渠道：真实 WhatsApp Web 登录态。
- 消息来源：用户用另一个 WhatsApp 账号给当前登录账号发送消息。
- 验收范围：采集、事件入库、长期记忆、语义事件、日程、主动建议、聊天问答。
- 副作用限制：不真实发消息、不付款、不投递、不点击外部 Apply/Submit。

## 相对时间解析规则

- “今天”应解析为 2026-07-02。
- “明天”应解析为 2026-07-03。
- “后天”应解析为 2026-07-04。
- “周五”在本轮测试中默认应解析为 2026-07-03，除非上下文明确指向下周。
- 所有展示给用户的日程必须展示绝对日期，不能只展示“明天”“周五”。

## 每批通用验收步骤

1. 用户按批次把消息发送到 WhatsApp。
2. 等待采集 worker 处理完成。
3. 检查 `events` 是否有对应 WhatsApp 原始事件。
4. 检查 `semantic_events` 的 intent、primary_label、confidence、slots 是否合理。
5. 检查 `agenda_items` 是否只为真正的约定、提醒、截止日期创建。
6. 检查 `proactive_suggestions` 是否必要、去重、内容可读。
7. 在 Android 悬浮窗或 App 对话中提问，确认召回真实上下文。
8. 记录 trace id、实际输出、结论和失败原因。

## 通过标准

- 应创建日程的消息必须创建，并且日期时间、地点、参与人、缺失字段合理。
- 不应创建日程的普通聊天、偏好、天气闲聊不能误创建日程。
- 相对时间必须转换为绝对日期。
- 主动建议不能重复刷屏，不能把普通聊天当成待办。
- 用户问答必须召回对应 WhatsApp 记忆或日程，不能说“没有记录”。
- 消息气泡中的长链接不能横向溢出。
- 悬浮窗和完整 App 的对话历史必须一致。

## 2026-07-02 实际线上验证记录：D4 家庭关系事实

### 复现

用户在真实 WhatsApp 里连续发送多条自然消息，其中包括：

> 我儿子叫王刚

随后在 Nomi 中问：

> 谁儿子叫王刚

### 初始实际结果

- Nomi 回复没有关于“王刚”及家庭关系的信息。
- 线上 `/api/chat` 的上下文中没有 `王刚` 相关证据。
- 数据库 `events` 里最初只看到 WhatsApp chat list preview 的最新几条消息，例如“我想买个你之前说的那个保险”和“明天下午在保利广场详细聊一下呗”，没有“我儿子叫王刚”。

### 根因

问题不是模型回答能力，而是采集链路漏消息：

1. WhatsApp 页面当时停在会话列表。
2. 采集器过度依赖 `chat_list_preview`，一个联系人在列表中通常只展示最新一条预览。
3. 用户连续发送多条消息时，中间事实会被后续消息覆盖，导致 `events` 没有原始事实。
4. 即使用户问“谁儿子叫王刚”，旧路由也没有稳定把家庭关系问题判定为记忆/关系查询，检索词还会保留整句“谁儿子叫王刚”，而不是抽出核心对象“王刚”。

### 已修复

- `runtime_api/app/chat_router.py`
  - 新增家庭关系问题路由。
  - “谁儿子叫王刚”会走 `relationship_query`，并开启 KV、图谱、RAG、时间线召回。
- `runtime_api/app/main.py`
  - 新增家庭关系对象抽取。
  - “谁儿子叫王刚”的检索 token 优先为“王刚”。
- `worker/app/worker.py`
  - 新增家庭关系事实规则抽取。
  - “我儿子叫王刚”会规则优先写成 `subject=user / predicate=son_name / object=王刚`。
- `chromium_runtime/app/runtime.py`
  - 当 WhatsApp 仍停留在会话列表且没有打开具体聊天时，自动打开最新聊天，使下一轮能同步完整可见历史，避免只采集最后一条列表预览。
